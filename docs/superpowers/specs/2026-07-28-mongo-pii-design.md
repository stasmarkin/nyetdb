# PII для MongoDB (шаг PII-M1) — дизайн

Статус: одобрен 2026-07-28. Снимает hard error `ConfigError::PiiUnsupported`
для `[connections.X.pii]` на mongodb-коннекшенах.

## Ключевая идея

В SQL сетка B стоит на провенансе колонок от сервера. В mongo провенанса нет,
но результат самоописан: документ несёт имена своих полей на всех уровнях.
Поэтому пара сеток инвертируется:

- **Сетка A** отказывает по любому *упоминанию* защищённого имени в запросе —
  как ключа (`{email: {$gt: ...}}`) и как строковой ссылки (`"$email"`,
  `"$$this.ssn"`). Это закрывает и оракул через filter, и все переименования:
  чтобы вынести значение под чужим именем, поле надо назвать.
- **Сетка B** — рекурсивный скан BSON результата: ключ с защищённым именем на
  любой глубине → deny отказывает весь ответ, mask редактирует значение на
  месте.
- Конечный список операторов перемещает значение, *не называя* поле
  (конверсия имена↔значения): `$objectToArray`, `$arrayToObject`, `$getField`,
  `$setField`, `$unsetField`. На PII-коннекшене они запрещены. `$replaceRoot`,
  `$$ROOT`, `$lookup` запрещать не нужно: они таскают документ вместе с его
  ключами, и скан их видит.

Гарантия: значение защищённого поля не покидает nyet — ни под своим именем
(скан), ни под чужим (отказ по упоминанию + запрет name/value-конверсий), ни
битом через filter (отказ по упоминанию).

## Решения (зафиксированы с пользователем)

1. **Умеренное сужение субсета.** `aggregate` остаётся; на PII-коннекшене
   урезается allowlist операторов (пять конверсий выше), сетка A начинает
   инспектировать строковые значения.
2. **Суффиксная семантика.** Правило `users.email` защищает имя `email` на
   любой глубине — и в упоминаниях запроса, и в ключах результата. Ложные
   срабатывания на одноимённых полях принимаются (fail-closed).
3. **Deny + mask одним шагом.** Скан один и тот же; mask — редакция по ключу
   на месте.

## Конфиг и правила

- `mode = "deny" | "mask"` как в SQL; `reject_env_vars_in_policy` уже
  покрывает `pii.*` на сыром toml — изменений не нужно.
- Правило — строго `collection.field` (два сегмента). `users.profile.ssn` —
  ошибка конфига с текстом «в mongo защита идёт по имени поля на любой
  глубине; напишите `users.ssn`». Правило, которое выглядит точнее, чем
  работает, — ложная уверенность (рефлекс finding 7).
- Скоупинг плоский, как в SQL: защищённые имена всех коллекций, названных в
  запросе (корневая + `from`/`coll` у `$lookup`/`$graphLookup`/`$unionWith`),
  сливаются в одно множество. Атрибуция поля к коллекции после `$lookup`
  недоказуема — не пытаемся.

## Сетка A (`mongo::classify`, только при непустой политике)

1. **Ключи документов** везде (filter, projection, sort, тела stages, `let`,
   литералы внутри `$eq` и т.п.): ключ режется по `.`, любой сегмент в
   защищённом множестве → `PII_COLUMN`. Литерал `{$eq: {ssn: "..."}}`
   ловится сознательно: это оракул подбором.
2. **Строковые значения** `"$path"` / `"$$var.path"`: срезать префикс,
   порезать по `.`, тот же матч.
3. **Строковые аргументы-имена**: ключ `distinct`, `localField` /
   `foreignField` / `as`, путь `$unwind`, аргументы `$count` и `$sortByCount`.
4. **Запрет пяти операторов** name↔value-конверсии → `PII_UNPROVABLE` с
   hint'ом про превращение имён полей в значения.
5. **Mask-исключение** (аналог «простой проекции» SQL): под mask защищённое
   имя разрешено ровно как ключ с литеральным `0/1/true/false` в
   projection-позиции (`find`-projection, `$project`, `$unset`) — поле либо
   не приедет, либо приедет под своим именем и будет заредактировано сканом.
   Всё остальное — отказ в обоих режимах.

## Сетка B (`read_reply`, до сериализации в extjson)

Рекурсивный обход каждого `Bson`, попадающего в rows (включая ветку
`distinct`, где значения бывают документами): ключ с защищённым сегментом →

- **deny**: весь ответ отбрасывается, `QueryOutcome::PiiRefused`
  (`PII_COLUMN`, exit 5) — тот же путь, что у SQL-сетки B. `judge_origins`
  для mongo обходится: его роль выполняет скан (иначе `Origin::Unknown` дал
  бы безусловный `PII_UNPROVABLE`).
- **mask**: значение (любого типа, NULL включительно) → `"[REDACTED]"`,
  warning `PII_MASKED` с именами полей. Правило SQL «обещано маске, но не
  заредактировано → отказ» вырождается: скан и есть редактор.

Fail-closed цена (в доки): одноимённое поле в любой вложенности попадает под
правило; `{$project: {email: {$literal: 1}}}` создаст ключ, который скан
заредактирует/отвергнет, хотя PII там нет.

## Остальные команды

- `nyet schema`: пометка `pii deny|mask` у путей, чей сегмент защищён.
- `nyet doctor`: привилегий уровня поля в MongoDB нет — честный `warn` с
  рецептом (view без защищённых полей + роль с `find` только на view), без
  пробы. Не `ok`: слоя 3 здесь нет.
- Сокрытие текста ошибок БД включается само (`redact_db_errors` смотрит
  только на непустоту политики); комментарии «mongo сюда не доходит» умирают.
- `agent-setup`: абзац про PII расширяется на mongo.

## Коды, тесты

- Коды переиспользуются: `PII_COLUMN`, `PII_UNPROVABLE`, `PII_MASKED`,
  exit 5. Новых нет.
- Юниты: коллектор упоминаний (ключи с точками, `"$$this.x"`, литералы),
  скан (вложенность, массивы, NULL, dotted keys).
- Корпус: `tests/corpus/mongo/pii.yaml` в формате SQL-собрата.
- Интеграционные (testcontainers): `$lookup`-встраивание, `$replaceRoot`-сдвиг,
  ловимый сканом, отказ `$objectToArray`.
- W7: новая поверхность «вынести значение mongo-поля, не назвав его».

## Остаточные дыры (в SECURITY.md)

- Существование/количество: `countDocuments({profile: {$exists: true}})` на
  родительском пути отдаёт бит о наличии субдокумента — не о значении.
  Принято.
- Полнота списка из пяти операторов — главный риск дизайна; проверяется W7;
  список закрыт allowlist'ом (новый оператор в OPS не появится без ревью).
