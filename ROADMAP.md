# nyetdb — Roadmap

CLI-утилита на Rust для доступа к базам данных, ориентированная на AI-агентов
(Claude Code, Cursor и т.п.) и harness'ы.

> **Your AI agent can look. For everything else — nyet.**

**Имя:** бренд/репозиторий/крейт — `nyetdb`, бинарник — `nyet` (паттерн
ripgrep→`rg`: бренд уникален и гуглится, команда короткая). Застолблено
(июль 2026): GitHub (stasmarkin/nyetdb), crates.io (`nyetdb` + алиас `nyet`).
**Бэклог:** зарегистрировать npm-пакеты `nyetdb` и `nyet` (имена свободны,
плейсхолдеры лежат в `packaging/npm/`; публикация упёрлась в браузерный
2FA-флоу npm — выполнить из каждой папки интерактивный `npm publish
--registry=https://registry.npmjs.org/ --access public` или завести granular
token с bypass 2FA). Домены — отложено (решение: пока не покупаем).

**Позиционирование:** safety-first CLI. Дифференциация — не широта поддержки баз
(там Google MCP Toolbox с ~47 источниками), а связка **plain CLI + layered
read-only + directory scoping + agent UX** (структурированные подсказки, schema
introspection, auto-guardrail через EXPLAIN). Ниша подтверждена исследованием
(июль 2026): universal CLI (usql) не имеют валидации запросов, AI-конкуренты
(MCP Toolbox, DBHub) пошли по пути MCP-серверов; бенчмарки показывают, что CLI
для агентов дешевле по токенам и не хуже по success rate. Пространство имён и
ниша «сдержи AI-агента» активно разбираются (nono, leash, declaw — все 2025–26).

## Принципы

- **CLI-first.** Если MCP-режим когда-нибудь понадобится (только по явному
  запросу пользователей — см. «Сознательно вне скоупа»), это обёртка из того же
  бинарника, не наоборот.
- **Layered security, не один слой.** AST-валидация (sqlparser-rs, fail-closed) +
  сессионный read-only (`default_transaction_read_only=on`, `SET TRANSACTION READ
  ONLY`, single-statement) + рекомендация read-only роли/реплики (`nyet doctor`).
  Наивный allowlist по `Statement::Query` недостаточен (writes внутри CTE и т.п.).
- **Конфиг создаёт только пользователь.** Креденшалы не попадают в контекст LLM —
  агент оперирует алиасами.
- **Directory scoping — UX-барьер, не security boundary** (cwd спуфится агентом).
  Честно документируем; настоящая граница — слои read-only.
- **nyet разговаривает с агентом**: поле `warnings` в ответе (обрезка, тайминги,
  отсутствие индексов), а не просто данные. Отказ — это фича и бренд: код `NYET`.

## Стек

| Область | Выбор |
|---|---|
| PostgreSQL / MySQL / MariaDB / SQLite | sqlx (динамический `query()`, MSSQL не поддерживается) |
| Redis / Valkey | redis-rs (`tokio-comp`, низкоуровневый `cmd()`; классификация write-команд — родной `COMMAND INFO`) |
| MongoDB | официальный крейт `mongodb` (своя read/write-классификация команд) |
| Cassandra / ScyllaDB | крейт `scylla` (отложено, по спросу) |
| SQL-валидация | sqlparser (apache/datafusion-sqlparser-rs), фича `visitor` |
| CLI / конфиг / вывод | clap, serde + toml (+ env-подстановка `${VAR}`), serde_json |
| Runtime | tokio |
| Композиция драйверов | cargo feature flags; релизный бинарник — со всеми |
| SSH-туннели | шелл-аут в системный `ssh` (наследует ~/.ssh/config, agent, ProxyJump); russh — только по жалобам |
| Дистрибуция | dist (форк astral-sh/cargo-dist): GitHub Releases, shell installer, Homebrew, npm-обёртка. Крейт `nyetdb`, `[[bin]] name = "nyet"` |

## Приоритет баз

1. **PostgreSQL** — MVP, эталонный вертикальный срез.
2. **MySQL/MariaDB, SQLite** — почти бесплатно поверх sqlx; SQLite = демо и локальные `.db` агентов.
3. **Redis** — дешёвая реализация, частый сценарий «посмотри что в кэше».
4. **MongoDB** — большая аудитория, дороже из-за своей классификации команд.
5. **ClickHouse** — вместо Cassandra в приоритете: популярен у девелоперов,
   analytics-запросы от агентов, родной `readonly=1`, диалект есть в sqlparser-rs.
6. Cassandra/ScyllaDB, MSSQL (tiberius), Elasticsearch, DWH — по запросам пользователей.

### v0.5 — экосистема

- [ ] Connection daemon: фоновый пул живых DB-соединений (unix socket 0600,
      idle-kill 15м, автоспавн/автовыход, паттерн gpg-agent). Триггер — замеры
      латентности после MVP (ControlPersist уже снял стоимость туннеля; демон
      нужен, если 50–300 мс TLS/auth всё ещё мешают или из-за topology discovery
      MongoDB). Замеры проведены, и они сместили приоритет: доминировала не
      стоимость коннекта (4–6 round trip'ов), а болтовня протокола (10 на
      PostgreSQL, 12 на MySQL) и второй спавн `ssh` на каждый запрос (10.5 мс
      локально, ~118 мс через WAN-бастион). Вместо демона сделаны две дешёвые
      вещи — схлопывание control-стейтментов и переиспользование форварда (см.
      «Сделано вне вех»). Демон остаётся не сделан; решать заново по латентности
      TLS/auth и по topology discovery MongoDB
- [x] `nyet sample <alias> <table>` — сэмплирование данных. Сахар над кодпутём
      `query`: nyet сам пишет запрос (случайная выборка, по умолчанию 10 строк;
      `$sample` на MongoDB) и гонит его НЕИЗМЕНЁННЫМ конвейером — валидатор,
      guardrail, обе PII-сетки, лимит, форматтеры, одна запись в аудит. Если
      guardrail отказал случайной выборке как дорогой (`EXPENSIVE_QUERY`) —
      одна автоматическая попытка дешёвым `LIMIT`-запросом с warning'ом
      `SAMPLE_FALLBACK` («это первые строки, не случайные»); на любой другой
      отказ (PII, ошибка БД, timeout) повтора нет
- [x] PII-защита (per-connection колонки). Шаг PII-1: секция
      `[connections.X.pii] columns = ["users.email", ...]`, отказ всего запроса
      (`NYET`/`PII_COLUMN`/`PII_UNPROVABLE`, exit 5) по имени до выполнения и по
      провенансу колонок результата после; текст ошибки БД на таком коннекшене
      агенту не отдаётся. Шаг PII-2: `mode = "deny" | "mask"` — маска отдаёт
      простую проекцию защищённой колонки как `[REDACTED]` (любой тип, NULL
      включительно) с warning'ом `PII_MASKED`, всё остальное отклоняется как
      раньше, а колонка, пропущенная под маску, но не заредактированная по
      провенансу, даёт отказ (`mask` не может вернуть то, что вернул бы `deny`); PII-колонки помечаются в `nyet schema`, `nyet doctor` проверяет,
      закрыты ли они правами роли, `nyet agent-setup` объясняет это агенту.
      Regex-автодетект по значениям/именам, частичная маска и токенизация не
      планируются (утечка по кускам и оракул равенства). Шаг PII-M1 (июль
      2026): MongoDB — сетки инвертированы, потому что провенанса от сервера
      нет, а результат самоописан: правило строго `collection.field` и
      защищает ИМЯ поля на любой глубине; сетка A отказывает по любому
      упоминанию (ключи, `"$field"`-ссылки, name-позиции `distinct`/`$lookup`)
      и запрещает операторы-конверсии имён↔значений (`$objectToArray` и др.,
      `PII_UNPROVABLE`); сетка B рекурсивно сканирует документы результата —
      deny отказывает весь ответ, mask редактирует по месту. Исключение mask —
      только литеральная 0/1-проекция. `doctor` честно говорит, что privileges
      уровня поля в MongoDB нет (рецепт: view + роль на view). Полнота списка
      операторов-конверсий — поверхность для W7
- [ ] Writes с opt-in: `allow_writes = true` в конфиге + `--unsafe-allow-writes`
- [ ] Кэш схемы

## Сделано вне вех

Работа, которой в вехах не было: всплыла по ходу и оказалась дешевле и нужнее,
чем то, что планировалось.

- [x] **TLS для прямых соединений** (rustls): `sslmode`/`ssl-mode` в url
      работают, MySQL 8 `caching_sha2_password` с паролем по TLS, warning
      `INSECURE_TRANSPORT` на незащищённом транспорте
- [x] **Managed-база за бастионом**: режим TLS переживает переписывание url под
      туннель (понижается только `verify-full` → `verify-ca`, не до `require`),
      а вежливое прощание (ROLLBACK + close) ограничено по времени и вынесено за
      дедлайн запроса — пулер, который не шлёт `close_notify`, больше не съедает
      уже полученный ответ
- [x] **Меньше round-trip'ов на запрос**: control-стейтменты схлопнуты в группы
      (PostgreSQL 10 → 7, MySQL 12 → 8; explain 8 → 5 и 10 → 6, schema на MySQL
      12 → 10). Имя таймаута на MySQL/MariaDB узнаётся один раз на соединение из
      ошибки 1193, а не перебирается на каждый SET. Гарантии guardrail'а не
      изменились: серверный cap взводится до любого агентского стейтмента, SQL
      агента по-прежнему едет отдельно по prepared-протоколу
- [x] **Переиспользование SSH-форварда между вызовами** (`reuse_forward = true`
      по умолчанию): один спавн `ssh` на запрос вместо двух, форвард переживает
      процесс и адоптируется следующим вызовом после проверки владения (реестр в
      `XDG_RUNTIME_DIR`, он же лок; `ssh -O check` должен вернуть тот же pid
      мастера). Замерено на стенде: 66.4 мс без reuse, 55.1 мс с ним. Цена
      записана честно в README: loopback-listener к базе живёт между вызовами,
      пока жив мастер
- [x] **Запрет advisory-локов PostgreSQL** (все 11 имён семейства, список взят
      из живого каталога): сессионный advisory-лок переживает ROLLBACK, а
      блокирующий висит до statement_timeout — write-образный эффект от
      read-only инструмента. Чтение состояния локов (`pg_locks`, `is_free_lock`)
      остаётся разрешено
- [x] **`justfile`**: `test-fast` (юниты + cli без Docker, секунды), `test`
      (всё, с контейнерами), `check` (fmt + clippy + тесты + deny + audit),
      `build`/`install`. `DOCKER_HOST` резолвится сам, при мёртвом демоне —
      внятная строка вместо стектрейса testcontainers
- [x] **Креденшалы вне конфига** (`password`/`url` = литерал ИЛИ ссылка на
      источник: `{ keychain = "item" }` / `{ env = "VAR" }` / `{ command = "..." }`;
      `password_env` удалён). Задача была не «пароль не в файле», а «агент не
      получает пароль, найдя файл» — а он работает под тем же uid, поэтому
      границу даёт только источник, проверяющий, КТО спрашивает. На macOS это
      Keychain: item, созданный самим nyet, несёт ACL с его подписью. Отсюда два
      правила, оба легко потерять: никакого шелл-аута в `/usr/bin/security`
      (тогда доверенным приложением станет `security`, который агент запустит
      сам) и item создаёт nyet, а не Keychain Access. Чтение идёт с выключенным
      UI, поэтому агентский запрос получает код ошибки, а не диалог на экране
      человека. Замерено прототипом: свой бинарь читает молча, `security`
      упирается в запрос пароля keychain, пересобранный nyet получает
      `errSecAuthFailed` (-25293) без диалога, перезапись item — снова запрос
      пароля. Отсюда `nyet secret-set <item>`: значение читается со stdin (не из
      argv — тот виден в `ps`), а после каждой установки nyet команду надо
      повторить, потому что ACL привязан к cdhash. `env`/`command` остаются как
      незащищённые источники, и `doctor` называет класс нейтральной строкой-фактом.
      Что НЕ закрыто и записано в SECURITY.md: конфиг принадлежит тому же
      юзеру, поэтому агент может переписать `url` (или добавить `[ssh] remote`)
      на свою базу и заставить nyet отдать ей настоящий пароль — модель угроз
      остаётся «кооперативный, но ошибающийся агент», не фишинг

## Хотелки (без вехи)

Идеи, которые хочется, но приоритет и дизайн ещё не зафиксированы. Попадают в
веху, когда станет ясно решение и найдётся спрос.

### W1 — Wire-протокол для обычных клиентов (TablePlus, DataGrip через nyet)

`nyet serve <alias>` слушает localhost как PostgreSQL-сервер (крейт `pgwire`),
GUI-клиент коннектится к нему, а не к базе; каждый запрос проходит тот же
пайплайн — валидатор, read-only, guardrail, PII, аудит. Ценность: те же гарантии
для человека за GUI, что и для агента, плюс один SSH-туннель на всех.

Открытые вопросы:
- Скоуп больше, чем кажется: extended query protocol (parse/bind/execute),
  prepared statements, COPY, cancel-request, аутентификация клиента к самому
  nyet, типы в `RowDescription`.
- GUI-клиенты шлют десятки интроспекционных запросов и служебных `SET` при
  коннекте — fail-closed валидатор их отобьёт. Нужен отдельный режим доверия к
  собственному интроспекшену клиента, иначе TablePlus просто не откроется.
- MySQL/Mongo/Redis — каждый свой протокол; реалистично начать и, возможно,
  остаться на PostgreSQL.
- Конфликт с принципом «CLI-first»: это ещё один фронт (как и MCP, который уже
  вынесен вне скоупа). Может оказаться дешевле сказать «нет» и оставить GUI
  прямое подключение read-only ролью.

### W3 — Кастомный резолв SSH-хоста скриптом

Адрес живой ноды не всегда статичен: кластер, автоскейлинг, лидер меняется.
Хочется `[connections.X.ssh] host_cmd = "..."` — nyet исполняет команду,
берёт из stdout хост (или `host:port`) и подставляет в ssh. Разово на коннект,
результат живёт столько же, сколько ControlPersist-туннель.

Открытые вопросы:
- Та же дисциплина, что у W2: запрет `${VAR}`, таймаут, ошибка команды = отказ
  коннекта (fail-closed), stderr скрипта не отдавать агенту дословно.
- Взаимодействие с `reuse_forward`: адоптированный форвард может указывать на
  ноду, которая уже не лидер. Нужен ключ переиспользования, учитывающий
  результат `host_cmd`, иначе получим тихое подключение не туда.
- Стоимость: скрипт вида «сходи в kubectl» — это секунды на каждый холодный
  коннект; надо решить, кэшируем ли результат и где.
- Дешёвая альтернатива, которая может закрыть 80%: `Match exec` в `~/.ssh/config`
  — nyet уже наследует пользовательский ssh-конфиг и ничего делать не нужно.
  Проверить на реальном кейсе до того, как городить `host_cmd`.

### W4 — Матрица тестов на реальных docker-образах

Фундамент уже есть: testcontainers поднимает `postgres:16-alpine`, `mysql:8.4`,
`mariadb:11.4` и SSH-стенд (digest-pinned), тесты не `#[ignore]`, CI их гоняет.
Хочется вширь и вглубь — по одной версии на движок мало: поведение таймаутов,
типов и `EXPLAIN` разъезжается между мажорами, а нас ловит именно на них.

Чего хочется:
- Матрица версий: PostgreSQL 13…17, MySQL 8.0/8.4, MariaDB 10.11/11.4,
  MongoDB 6/7/8, дальше — движки из W8/W9, если их сделаем, теми же
  контейнерами.
- Версия образа — параметр (env/фича), а не константа в тесте; локально одна
  дефолтная, в CI — полная матрица (nightly, не на каждый PR: время и лимиты
  GitHub Actions).
- Долгоживущий стенд для локальной разработки: контейнеры переиспользуются между
  прогонами вместо подъёма на каждый тест — сейчас это главная цена `cargo test`.
- Что именно матрица обязана покрывать: серверные таймауты и их SQLSTATE,
  декодирование типов, форма `EXPLAIN` для guardrail, провенанс колонок для PII.

Открытые вопросы:
- Стоимость: полная матрица — десятки контейнеров, время CI и flakiness растут
  нелинейно. Возможно, вглубь важнее, чем вширь: не «все мажоры», а oldest +
  newest supported.
- Переиспользуемые контейнеры — грязное состояние между тестами; нужна
  дисциплина уникальных схем/БД на тест, иначе получим плавающие падения.
- `just test` должен остаться «просто работает» без Docker-инструкций в голове:
  один рецепт на быстрый прогон (без контейнеров) и один на полный.
  **Сделано:** `justfile` — `test-fast` (без Docker) и `test` (с контейнерами),
  `DOCKER_HOST` резолвится сам; см. «Сделано вне вех».

### W5 — Линтеры и практики безопасной разработки

Базовый слой уже стоит и его надо не потерять, а не изобретать заново:
`#![forbid(unsafe_code)]`, `cargo fmt --check`, `cargo clippy --all-targets -D
warnings`, `cargo deny` (закрытый allowlist лицензий, `yanked = "deny"`),
`cargo audit`, экшены запинены на полные SHA, `permissions: contents: read`.

Что делаем (решения приняты):
- **Паника валидатора — это баг, а не отказ.** Сейчас паника в разборе выходит
  крэшем: fail-closed формально соблюдён, но exit code чужой и записи в аудите
  нет. Вызов валидатора оборачивается в `catch_unwind`, паника мапится в штатный
  отказ — тот же exit code, та же строка в `audit.jsonl`. Иначе каждая находка
  фаззера — отдельный класс инцидента вместо обычного «нет».
- **Фаззинг в два уровня, и главный из них не `cargo-fuzz`.** Генератор SQL на
  `proptest` из грамматики с известными write-узлами и инвариантом «есть
  write-узел ⇒ валидатор отказал» — он проверяет ровно заявленную гарантию и
  живёт в обычном `cargo test`. Второй уровень — `cargo-fuzz` на panic-freedom по
  сырым байтам: отдельный `fuzz.yml` по расписанию (nightly, ~15 минут на таргет),
  падение заводит issue с репро, репро-кейсы коммитятся в корпус и становятся
  детерминированными регрессиями. OSS-Fuzz — после публичного релиза: до него
  туда просто не с чем приходить.
- **Дифференциальный тест на контейнерах из W4.** Оракул — серверный read-only:
  всё, что валидатор пропустил, исполняется под ним на PostgreSQL и MySQL
  (testcontainers) и на SQLite in-process; что сервер завернул как запись, а
  валидатор пропустил — дыра. Плюс проверка однооператорности через `PREPARE`:
  сервер ругается на второй стейтмент там, где валидатор увидел один. Вход —
  `tests/corpus/*` и тот же proptest-генератор. Снапшот-дифф состояния БД
  до/после откладываем в W7 и делаем точечно на подтверждённых векторах: на всём
  корпусе он дорог и почти всегда пуст.
- **MSRV — фактический, а не желаемый.** `cargo msrv find`, результат в
  `rust-version` в `Cargo.toml`, джоба `cargo check` на этом тулчейне. Бампаем
  свободно, обещание ровно одно: он указан и он проверяется.
- **`SECURITY.md` — канал приёма и честный список дыр.** Канал — GitHub Private
  Vulnerability Reporting (не почта: ящик надо заводить и охранять),
  поддерживается только последний релиз. Главное в файле — ЯВНЫЙ перечень того,
  что nyet не гарантирует: directory scoping это UX-барьер, а не песочница;
  prompt injection на нашем слое не лечится; оракул на защищённой колонке через
  `WHERE` отдаёт бит информации. Честность вместо obscurity: ненаписанную границу
  всё равно найдут, только не мы.
- **Branch protection без ритуального ревью.** Required status checks, запрет
  force-push, linear history. Required review — нет: мейнтейнер один, и
  самоапрув для галочки хуже честно отсутствующего ревью. OpenSSF Scorecard
  включаем как есть и за балл не воюем — это индикатор, а не цель.
- **Мелкие линтеры ценой одной строки в CI.** `typos` (в исключениях
  `tests/corpus/` — там данные, и кириллические доки), `cargo-shear` вместо
  `cargo-udeps` (stable, без сборки), `zizmor` на воркфлоу — SHA-пины это ещё не
  безопасный workflow.
- **Provenance — встроенный в dist, а не свой.** `github-attestations` в
  `dist-workspace.toml` плюс права `id-token`/`attestations` в `release.yml`;
  точное имя опции для dist 0.28.7 — **сверить** по докам, память тут не аргумент.
- **CodeQL — по факту, а не по вере.** ✅ Rust в CodeQL — GA с 2025-10-14
  (CodeQL CLI 2.23.3+, changelog GitHub), проверено 2026-07-27. Заведён
  `.github/workflows/codeql.yml`: `push` на main + `pull_request` + weekly
  `schedule`, `languages: rust` / `build-mode: none`, `github/codeql-action`
  init+analyze запинены на SHA (v4.37.3), `security-events: write` только в этой
  джобе.
- **`cargo-mutants` на валидатор — разовый эксперимент вне CI.** Он покажет,
  какие мутации граничной логики тесты не замечают; по результату решим, нужно ли
  расписание.
- **Dependabot** на `github-actions` и `cargo`, еженедельно: SHA-пины без
  автообновления — это не безопасность, а протухшие версии.

Отвергнуто сознательно: `cargo-semver-checks` (бинарный crate, публичного API
нет), Miri (`unsafe` запрещён `forbid`ом, проверять нечего), линт
conventional-commits.

### W7 — Адверсариальный аудит: как сломать read-only

Отдельная работа, а не подпункт W5: посадить агентов ломать гарантию «только
чтение» и превратить найденное в тест-корпус (`tests/corpus/*_deny.yaml` — уже
готовый формат для этого).

Поверхности атаки, с которых начинать:
- **Расхождение диалектов.** sqlparser разбирает текст не так, как сервер:
  вложенные комментарии, dollar-quoting, `E''`-эскейпы, юникод-омоглифы и
  нормализация идентификаторов, `;` внутри литерала. Всё, что валидатор считает
  `SELECT`, а сервер — не совсем.
- **Побочные эффекты внутри чтения.** `SELECT` вызывающий функцию, которая пишет:
  `setval()`, `lo_export`, `pg_read_file`, `dblink`, `COPY ... PROGRAM`, вызов
  volatile-функции пользователя. Слой валидатора про функции знает
  (`allow_functions`/`deny_functions`), но полнота списка не доказана.
- **Обход сессионного read-only**: `SET`/`RESET` в обёртке, которую валидатор не
  распознал как transaction control; функции, открывающие свою транзакцию.
- **Многооператорность**: всё, что заставляет драйвер отправить два стейтмента
  там, где валидатор увидел один.
- **PII/guardrail**: провенанс колонок через `UNION`, оконные функции, `RETURNING`,
  `CASE`, приведение типов; оракул на защищённой колонке через `WHERE`
  (сравнение не отдаёт значение, но отдаёт бит информации) — известная и
  сознательно принятая дыра, но границу надо записать явно.
- **Аудит и туннель**: заглушить `audit.jsonl` (путь, права, симлинк) или
  подцепить чужой `-L` форвард при `reuse_forward`.

Результат работы — не отчёт, а зелёные тесты на каждый подтверждённый вектор
плюс честный список того, что защитить нельзя, в `SECURITY.md` (W5).

**Первый проход сделан (август 2026): PostgreSQL, побочные эффекты внутри
чтения.** Замеры на живом `postgres:16-alpine`, критерий тот же, которым
заслужили место `nextval`/`setval`: функция запускается внутри `BEGIN READ
ONLY` — значит слой 2 её не ловит. Найдено и закрыто денилистом (+24 кейса в
`postgres_deny.yaml`): назначение XID (`txid_current`, `pg_current_xact_id` —
единственное семейство, которое проходит и слой 3: три вызова сдвинули `xmax`
кластера на три, три обычных SELECT — ни на сколько), WAL/бэкап
(`pg_create_restore_point`, `pg_switch_wal`, `pg_rotate_logfile`,
`pg_backup_start`), слоты и origin'ы репликации (слот держит WAL и может забить
диск; `get_changes` продвигает слот, `peek_changes` — нет и остался разрешён),
`pg_stat_reset*` (префикс) и `pg_stat_statements_reset`, обслуживание индексов
(`brin_summarize_new_values`, `gin_clean_pending_list` — пишут в индекс сквозь
read-only), `pg_import_system_collations`, `pg_notify` и `set_config` (это `SET`
в обёртке из функции, а сам `SET` давно отказывается как TXN_CONTROL).

Проверено и НЕ подтвердилось: механизм денилиста не обходится квалификацией,
регистром или кавычками (`pg_catalog."PG_SLEEP"` ловится); `set_config
('transaction_read_only','off')` сервер запрещает сам; снятый через `set_config`
`statement_timeout` не спасает уже идущий запрос — таймер взведён. Последнее
станет реальным вектором, когда появится connection daemon (v0.5): сессия
переживёт вызов.

**Второй проход (август 2026): MySQL/MariaDB и SQLite.** На `mysql:8.4`
замерено: `asynchronous_connection_failover_add_source(...)` выполняется внутри
`START TRANSACTION READ ONLY` и оставляет строку в
`mysql.replication_asynchronous_connection_failover` — durable запись в
системную таблицу из «чтения»; останавливают только права
(SUPER/REPLICATION_SLAVE_ADMIN). Закрыто вместе с семейством failover, а по
классу (плагин в стоковом сервере не загружен, замерить нельзя — помечено в
коде честно) — `group_replication_*` (переключение primary!), `keyring_*`
(хранит и ОТДАЁТ ключи), `version_tokens_*`, `flush_rewrite_rules`,
`audit_api_message_emit_udf`, `service_*_locks`, `masking_dictionary_*`.

**Находка на SQLite, которую денилист не лечит:** движок встроен в процесс, а
guardrail'а на SQLite нет (сервер не публикует оценок), поэтому запрос ест
память самого `nyet`. Замерено: `randomblob(1e9)` → 994 МБ, а рекурсивный CTE с
удвоением строки → **4.35 ГБ за 4 секунды**, вообще без «опасных» функций.
Денить `randomblob`/`zeroblob` бессмысленно — CTE-форма и проще, и мощнее.
Собственные лимиты SQLite тоже не помогают: `hard_heap_limit` в этой сборке не
скомпилирован (читается как 0), `soft_heap_limit` ограничивает кэш страниц, а
не строки (при 256 МБ тот же запрос дал 4.13 ГБ). Записано в SECURITY.md как
принятое ограничение с рецептом снаружи (ulimit/cgroup/контейнер).

Проверено и НЕ подтвердилось: MariaDB сама отбивает `NEXTVAL`/`SETVAL` внутри
READ ONLY («Cannot execute statement in a READ ONLY transaction») — в отличие от
PostgreSQL, где именно поэтому `nextval` в денилисте; оптимизаторные хинты
(`/*+ MAX_EXECUTION_TIME(...) */`, попытка поднять серверный лимит времени) и
executable-комментарии `/*! */` отбиваются как EXECUTABLE_COMMENT; `INTO
OUTFILE`/`DUMPFILE`, `DO`, `HANDLER`, `LOCK IN SHARE MODE` не парсятся →
fail-closed; в SQLite `sqlite_dbpage`, `sqlite_dbstat`, `sqlite_stmt` и `fsdir`
в сборку sqlx не включены и недостижимы (денить нечего).

**Третий проход (август 2026): парсер против сервера.** Найдено одно реальное
расхождение и один незаявленный барьер. Расхождение: при
`sql_mode=NO_BACKSLASH_ESCAPES` MySQL не считает `\'` экранированием, поэтому
`SELECT '\';SELECT 2;--'` для сервера — ДВА стейтмента, а для валидатора — один
литерал (замерено на обоих: валидатор `allow`, сервер выполнил `SELECT '\'` и
`SELECT 2`). Барьер: до сервера это всё равно не доезжает — запросы уходят
prepared-стейтментом, а он не принимает второй стейтмент; замерено через сам
`nyet` — сервер отбил всю строку синтаксической ошибкой. То есть
многооператорность должна победить и парсер, и wire-протокол. Записано в
SECURITY.md именно так: это свойство текущего способа отправки, а не обещание —
переход на простой query-протокол потеряет его молча.

Проверено и совпадает с сервером: вложенные комментарии (PostgreSQL вкладывает,
MySQL — нет, и валидатор диалект-специфичен: на MySQL отказывает там, где на
PostgreSQL разрешает), dollar-quoting, `E''`-эскейпы, `;` внутри литерала,
юникод (омоглиф в ключевом слове не парсится, zero-width вычищается
нормализацией, и выполняется именно нормализованный текст). Всё закреплено в
корпусе как спецификация.

**Четвёртый проход (август 2026): PII, аудит, туннель.**

PII-сетки держат. На живой базе с `columns = ["users.email"]` отбиты все
попытки увести значение мимо имени: алиас, подзапрос с переименованием, `CASE`,
`::text`, конкатенация, `max()`/`string_agg()`, `row_to_json(u)`/`to_jsonb(u)`
(вся строка одним выражением), скалярный подзапрос, оконная функция, `UNION ALL`
со сдвигом позиции, `SELECT u FROM users u` (whole-row). Каталоги статистики
(`pg_stats.most_common_vals`, `pg_statistic`), где значения колонок лежат как
ДАННЫЕ, тоже уже перекрыты (`value_sampling_catalogs`). Фильтр и сортировка по
защищённой колонке отказываются — оракул закрыт для прямого упоминания.

Подтверждено заявленное ограничение: **view над защищённой таблицей отдаёт
PII** (`SELECT email FROM people`, где `people` — view над `users`), потому что
правило привязано к имени отношения, а провенанс от сервера указывает на view.
Это записано в SECURITY.md, а теперь и `doctor` про такие view не молчит: чек
`pii_views` (PostgreSQL) обходит `pg_depend` и называет каждый view или
materialized view, который читает защищённую колонку И доступен этой роли на
SELECT. Не `information_schema.view_column_usage`: тот показывает только
таблицы, принадлежащие текущей роли, поэтому рекомендованная read-only роль
(которая не владеет ничем) всегда получала бы пустой ответ — ложное «всё
чисто», что хуже отсутствия проверки.

Аудит: fail-closed работает (лог недоступен на запись → `AUDIT_FAILED`,
результат агенту НЕ отдаётся), файл создаётся 0600. **Найдена и закрыта дыра:**
если путь лога вёл на `/dev/null` (напрямую или через симлинк, подложенный
агентом), `nyet` писал в никуда и спокойно отдавал результат — трейл молча
выключен, ровно обратное обещанию UX-8. Теперь тип проверяется на ОТКРЫТОМ
хендле (подмена пути после проверки не помогает): не обычный файл — отказ,
результат придержан. Симлинк на настоящий файл продолжает работать: правило про
то, что путь ХРАНИТ, а не про подозрительность симлинков.

Туннель: замера не делал (нужен ssh-стенд), инвариант разобран по коду. Он уже
называет свой остаточный риск честно и подробно — после `ssh -O cancel -L`
освободившийся эфемерный порт может занять любой локальный процесс, и
следующий запуск отправит туда handshake; именно поэтому `doctor` учит `-O
exit`, а не `-O cancel`. К этому стоит добавить очевидное: файл реестра
принадлежит тому же пользователю, что и агент, поэтому он не является
доказательством владения против НАМЕРЕННОЙ подделки — это тот же класс, что
агент-контролируемый путь аудита.

**Пятый проход (август 2026): MongoDB.** Тем же методом, на живом `mongo:7` с
политикой `users.email`. Сетки держат: `$lookup`, `$unionWith`, `$graphLookup`
из защищённой коллекции отбиты (правило keyed на имя, но обращение к коллекции
ловится), `$out` внутри `$facet` и внутри `$lookup.pipeline` — WRITE_OPERATION,
`$$ROOT` и `$getField` — PII_UNPROVABLE, метаданные-стадии (`$collStats`,
`$indexStats`, `$planCacheStats`, `$listSessions`, `$documents`) — вне
allowlist. Единственная слепая зона — та же, что на SQL: **view над защищённой
коллекцией**.

Поэтому `pii_views` сделан и для MongoDB: `listCollections` даёт `viewOn` и
пайплайн, а дальше каждый кандидат опрашивается через `$type` (отвечает
`"missing"`, а не значением, — диагностика не тянет защищённые данные в nyet).
Это важно не ради точности ради точности: `pii_columns` СОВЕТУЕТ создать view,
который `$unset`ит защищённые поля, и без этой пробы doctor ругался бы на
собственную рекомендацию. Прав на объекты MongoDB дёшево не проверить, поэтому
формулировка mongo-версии обещает ровно то, что проверено: «эти view отдают
поле», без утверждений о том, кто их может читать.

Осталось в W7: fuzzing и дифференциальное тестирование как непрерывный процесс
(инфраструктура есть — `fuzz/`, `validator/differential.rs`), Redis/ClickHouse —
когда появятся.

### W8 — Redis

Был в вехе v0.4, перенесён сюда: спрос не подтверждён, а работа не сводится к
«ещё один драйвер». Классификатор write-команд берётся из самого сервера —
`COMMAND INFO` отдаёт флаги (`write`, `readonly`, `admin`, `blocking`), то есть
в отличие от MongoDB свой перечень вести не надо.

Открытые вопросы:
- **Скриптинг.** `EVAL`/`EVALSHA`/`FCALL` помечены `write` не всегда, а сам скрипт
  на Lua валидатору непрозрачен — либо запрещать целиком, либо разбирать чужой
  язык (то, от чего мы ушли в MongoDB).
- **Читающие команды с побочным эффектом**: `GETEX` (меняет TTL), `SPOP`,
  `GETDEL`, `RANDOMKEY` в кластере, `SCAN` с курсором на сервере.
- **Слоя 2 нет вовсе**: read-only есть только у реплики (`replica-read-only`),
  а ACL (`+@read -@write`) — это слой 3, то есть та же история, что в MongoDB.
- **Что такое строка результата** для `HGETALL`/`LRANGE`/`XRANGE`: у Redis нет
  ни таблиц, ни документов, и контракт вывода (`columns`/`rows`) придётся
  натягивать — либо честно признать, что для Redis он другой.
- **`nyet schema`** без схемы и без коллекций: `SCAN` по пространству ключей —
  это скан прода, а `--bigkeys` тем более. Возможно, честнее `na`.

### W9 — ClickHouse

Был в вехе v0.4, перенесён сюда. Выглядит дешевле всех прочих движков —
диалект SQL, а `readonly=1` даёт настоящий слой 2 на стороне сервера, — но
дешевизна требует проверки.

Открытые вопросы:
- **Насколько sqlparser понимает диалект ClickHouse**: `FINAL`, `SAMPLE`,
  `PREWHERE`, `ARRAY JOIN`, движки таблиц, `SETTINGS` в запросе. Расхождение
  «как разобрал валидатор» и «что выполнит сервер» — корневой класс дыр (W7),
  и здесь он вероятнее, чем в Postgres/MySQL.
- **`readonly=1` против `readonly=2`**: первый запрещает и запись, и изменение
  настроек, второй разрешает менять настройки — то есть агент сможет поднять
  себе лимиты. Нужен `doctor`, который различает эти два и не выдаёт второй за
  первый.
- **Табличные функции** `url()`, `file()`, `s3()`, `remote()`, `jdbc()`,
  `executable()` — чтение, которое ходит наружу или исполняет код. Тот же класс,
  что `query_to_xml` в Postgres; денилист обязателен и его полнота — вопрос
  безопасности.
- **Guardrail**: `EXPLAIN ESTIMATE` даёт число строк и частей без выполнения —
  вероятно, лучший guardrail из всех движков. Проверить, что это так.
- **Стоимость**: официальный Rust-драйвер использует HTTP-интерфейс; надо
  посмотреть, что это делает с таймаутами, TLS и туннелем.

### W10 — Ввод запроса: `--file`/stdin и параметры вместо строки в argv

Сейчас `nyet query <alias> <query>` берёт запрос только позиционным аргументом,
опций `--file`/stdin нет. Многострочный запрос с кавычками внутри
(`WHERE slug IN ('a','b')`) приходится эскейпить под zsh — на 20 строках это
раздражает и порождает опечатки, которых в самом SQL не было. Хочется
`nyet query prod --file q.sql` и `nyet query prod -` (читать stdin), плюс
параметризацию — `--param slug=a --param slug=b` или `--params-json`, чтобы
значения не инлайнились в текст руками. Для read-only это не про безопасность,
а про то, что ручной эскейп строк — лишний источник моих же ошибок.

Открытые вопросы:
- Стиль плейсхолдеров разъезжается по движкам: `$1` в PostgreSQL, `?` в
  MySQL/SQLite, у Mongo своя история. Либо один нейтральный синтаксис
  (`:name`) с трансляцией на движок, либо честно «как в вашей базе» — второе
  дешевле, но ломает единый help.
- Типы параметров: из CLI всё приходит строкой, а `WHERE id = :id` на числовой
  колонке в PostgreSQL строкой не биндится. Нужен либо явный тип
  (`--param id:int=7`), либо JSON-вход, где тип уже есть.
- Взаимодействие с валидатором и PII: параметры проходят мимо AST, и это
  правильно — но проверить, что провенанс колонок и `deny`-правила по именам
  не завязаны на текст литералов.
- stdin уже занят? Проверить, не конфликтует ли чтение stdin с интерактивным
  вводом ssh (пароль/пассфраза) — `ssh` спавнится в том же процессе.
- Ограничение argv (`ARG_MAX`) — не реальная проблема на 20 строках, ради него
  городить не стоит; мотивация именно UX-ная.

### W11 — Дешёвый список имён таблиц

`nyet schema <alias>` целиком — это десятки килобайт (на живой базе ~27 КБ),
а точечный `nyet schema <alias> <table>` требует уже знать имя таблицы. Из-за
этого дешевле сходить в `information_schema` руками, чем тянуть общий дамп ради
одного имени. Хочется способ получить только перечень объектов — например
`nyet schema <alias> --names` (или `nyet tables <alias>`): имена таблиц и вью,
без колонок, индексов и FK.

Открытые вопросы:
- Флаг у `schema` или отдельная подкоманда: `--names` дешевле и не плодит
  поверхность, но `nyet tables` агент найдёт в `--help` быстрее (UX-3).
- Не пересекается ли с `nyet list`: там алиасы, здесь объекты — но имена команд
  рядом и путать их будут.
- Порог детализации у `schema` уже есть (details up to 50 objects) — возможно,
  правильный ответ не новый флаг, а более агрессивная деградация до имён на
  больших базах. Тогда цена нулевая, но поведение неявное.
- Для MongoDB «имена» — это коллекции, и они дёшевы; для Redis (W8) списка
  объектов нет вовсе.

### W12 — `agent-setup`: описания коннекшенов, соседство скиллов, размер

Отзыв от агента, которому скилл достался в работу (июль 2026). Три вещи, ни одна
пока не сделана.

**Описание на коннекшен.** Секция «Your connections» рендерит плоский
`alias  engine` (`src/skill.rs:266`), а `Conn` знает только эти два поля. На
32 алиасах из имени ничего не следует: `prod-1000-bazinga` vs `prod-1000` vs
`startrek` — агент угадывает шард или, хуже, идёт в прод там, где хватило бы
локального стенда. Генератор этого знать не может — знание есть только у
владельца конфига. Хочется `description = "..."` на коннекшен, которое
`agent-setup` дословно выводит рядом с алиасом (и, вероятно, `nyet list` тоже).

- Цена мала: поле в `Connection` + строка в рендере. Но у `Connection` стоит
  `deny_unknown_fields`, так что это изменение схемы конфига, а не аддитивная
  мелочь — старый nyet на новом конфиге упадёт.
- `${VAR}` внутри — запрещать? Это не политика, а текст, но текст едет прямо в
  контекст агента, и подмена через окружение = дешёвая инъекция инструкции.
  Скорее запрещать, как в `allowed_dirs`/`pii`.
- Длину надо чем-то ограничить: описание в 200 строк — это тот же скилл, только
  без ревью.

**Соседство с чужими скиллами.** Пользовательский скилл (в отзыве —
`tracker-mongo`) говорит «доступа к базе нет, попроси человека», сгенерированный
nyet-скилл — «выполняй сам». Какой подтянется, так агент себя и поведёт. Чинить
это правкой чужого скилла — работа пользователя, но `agent-setup` может помочь:
сказать в выводе команды (не в самом SKILL.md), что доменные скиллы про ту же
базу нужно перевести на nyet как транспорт, оставив им содержание — схему и
доменные различия, которых nyet не знает. Открытый вопрос: не превращается ли
это в советы про чужие файлы, которые мы не контролируем.

**Размер и прогрессивная загрузка.** ~11 КБ грузятся целиком при каждом
срабатывании, а `description` во frontmatter триггерится на любое чтение из БД.
Секция про защищённые колонки (~35 строк) нужна, только если в конфиге реально
есть `[connections.X.pii]`. Кандидаты: рендерить PII-секцию условно (данные у
генератора уже есть) и/или вынести редко нужное в отдельный reference-файл,
который агент читает по необходимости. Не блокер — делать, когда размер начнёт
мешать; замера токенов у нас всё ещё нет (см. v0.2).

### Сознательно вне скоупа

Дампы/бэкапы (write-территория, огромный скоуп), интерактивный REPL (есть
pgcli), курсорная пагинация (LIMIT + warning покрывают 95%).

**`nyet mcp` (MCP-режим).** Убран из плана работ: делать не хотим. Принцип
«CLI-first» сохраняется — если MCP когда-нибудь и появится, то обёрткой из того
же бинарника поверх готового пайплайна, — но только по явному запросу
пользователей, не проактивно. До такого запроса пространство MCP закрывают
конкуренты (MCP Toolbox, DBHub), и дифференциация nyet в другом (plain CLI +
layered read-only + agent UX).

## Известные риски и открытые вопросы

- sqlparser-rs — syntax-only: доля легитимных запросов, отбиваемых fail-closed,
  неизвестна до прогона на реальном корпусе (веха v0.1).
- `default_transaction_read_only` — сессионная настройка, теоретически
  откатывается через SET; компенсируется запретом SET/multi-statement на слое
  валидатора и рекомендацией read-only роли.
- Prompt injection через результаты запросов — полной защиты не существует;
  митигации: read-only scoping, аудит-лог, предупреждение в доках.
- Готовой поддерживаемой классификации write-команд для MongoDB/CQL нет —
  ведём свою (Redis закрыт через COMMAND INFO).
- Хранение креденшалов: MVP — файл 0600 + env-подстановка; вынос в менеджер
  секретов — хотелка W2.
- Имя `nyet` — обычное слово: SEO зарабатывается контентом и брендом `nyetdb`;
  холодновойный флёр — осознанное решение (панк-брендинг, самоирония автора).
